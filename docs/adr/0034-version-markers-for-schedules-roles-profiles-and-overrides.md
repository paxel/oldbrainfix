# Schedules, roles, Profiles and Overrides carry a version, and a value of a later one is kept read-only

A later version may change what a Routine's schedule, a grant in a Shared Area, a Profile record or an Override holds. Until now a Device of this version read such a value as nothing: the Routine vanished with its alarms, the grant was ignored so an earlier one stood or none, the Profile was refused, and any of them could be written over from here (#60, #131). Each now carries the version of its structure, by the rule of ADR 0019: a missing version means 1, and version 1 is never written. A value of a later version is kept as it came, shown as far as this version can, with "Saved by a newer version of Old Brain Fix. Update the app to change it." where the value would show, on the phone and on the desktop alike, and nothing on this Device writes it. Sync, the shared folder, bundles and Backups carry it byte for byte, as every entry. Pair codes, Sent Items, Backups, the shared folder's keys and Profiles files and local settings follow the same rule (#133): one of a later version says so instead of reading as none or as missing data.

## A version that is no version

Only an absent version and exactly 1 are version 1: the string `1` in a field of the log, the whole number `1` in JSON. Anything else, `2`, `01`, ` 1`, `1.0`, `"1"`, `0`, `null` or an empty string, counts as a later version. A text written in a structure not known is shown as its source (ADR 0018); a schedule, a role or a picture cannot be, so the safe reading of a garbled version is the one that changes nothing. Field values are compared as strings and never parsed as numbers, so both cores agree on every one.

## The markers

**Routine schedule.** The Routine carries `scheduleVersion`; version 1 holds `start`, `times` and `rule`. The schedule needs a newer version when `scheduleVersion` is anything but absent or `1`, or when its start, times or rule are there but not readable: a start that is no day, a time that is no `HH:MM` (one such time no longer drops out of the list unnoticed), an RRULE with a part not known, or a combination the schedule refuses. Fields without a start and without a version still hold no schedule, as before. Such a Routine reads as no Routine (`byId` and `all` leave it out), so it has no Agenda rows, alarms, calendar entries or calendar file and goes into no Sent Item; `newer`, `newerOfNote` and `noteOfNewer` list it for the apps, which show it in the list of all Routines and Reminders, under its Note, its card opening the Note. Reschedule, Re-nag, Escalation, trash and Done are refused; trashing or restoring its Note leaves it as it is. `scheduleVersion` belongs to the schedule's Conflict unit, but a version never written is no value of a Conflict version and a pick does not write it; a Conflict one of whose versions is a schedule not readable here is not resolvable here, as a text in a format not known (ADR 0018). A Sent Item update neither reschedules a Routine the receiver's later version changed so nor adds it again.

**Grants.** A grant is `{"profile":…,"role":…,"v":…}`. It needs a newer version when `v` is anything but absent or 1, when it holds a key besides these three, or when its role is not one this version knows; it still names a non-empty Profile id, else it is no grant. It counts like any grant: the person is listed among the people of the Area, their Devices go on getting it, and the grant names their person. It gives `AreaAccess.none` here: what such a Device writes into the Area stays in the log and applies on a Device that knows the role, not here. A Device holding such a grant counts as no Manager when it signs grants, adds no Devices of its own as a Member may, and may only end its own person's grants, as leaving does. Here nothing changes or ends it: changing the role of a person with such a grant and taking them out are refused, an invite leaves their Device as it is, and an own Device met in a sync or restored from a Backup is not handed a grant this version cannot write. A blocked person's grant of a later version is not kept (ADR 0021), and an Area offer whose grant for this Device is of a later version is not taken (#108). Before, a later role was ignored at judging, so the grant before it stood, or none, and a Manager here could write over it.

**Profile record.** The record is `{"id":…,"name":…,"picture":…,"v":…,"version":n}`, keys sorted. It is of a later structure when `v` is anything but absent or 1, or when it holds a key besides these five. Its `id` and `version` stay what they always were, needed to bind it and to tell which record replaces which; its name shows when it is a string and is empty otherwise, its picture when it is standard base64 and is made again, else none, where a version 1 record would be refused. Every record is kept as received and passed on unchanged (ADR 0017), so another person's needs nothing more. The own Profile of a later structure, taken from one of the user's Devices, changes its name and picture only there: renaming it or changing its picture here is refused, the system's defaults are no longer applied, and writing the same name or picture again changes nothing. A Profile card made from it carries the bare record as always, which the full one replaces wherever both arrive.

**Override.** The Override carries `overrideVersion`; version 1 holds `overrideName` and `overridePicture`. It is read like them, from what one's own Devices wrote only (ADR 0017), so another person's Device cannot lock an Override by writing one. Of a later version, its name and picture show as far as they read, and giving another name or picture is refused; the same again changes nothing. Names stay plain strings (ADR 0018); the marker is a field of its own.

## The database and Android's stored values

**Database.** The SQLite file each app keeps the log in records the version of its tables as `user_version` (#132). This version's tables are version 1. SQLite gives every file 0 until something is written there, so 0 is a database from before the version was recorded, and those tables are the same as version 1: every release since 0.1.0 has had the `ctx`, `raw` and `v` columns, so the column probes that added them are gone. Opening such a file writes 1. Unlike a marker in the log, this number is written for version 1 too: no other Device reads it, nothing syncs it, and it is what lets each later version's step run once, a check of the version where the columns were probed before. A later version adds its step, which ends by writing its number.

A file of any other version, a later one or a number no version writes, such as a negative one, is not opened. The store reads `user_version` first, before the journal mode, the tables, the Device key or the directories beside the file, and gives up with `StoreNeedsUpdate` (Dart) or `Error::StoreNeedsUpdate` (Rust), leaving every byte of the file and of everything beside it as it was. In place of the app the phone shows only "This Device's data was saved by a newer Old Brain Fix; install that version again." and "Nothing on this Device was changed.", before anything else and with no Capture; its background sync does nothing. On the desktop every start but the command line, the window's, the tray's and the capture popup's, shows the same in a window of its own and starts no tray, hotkey, alerts or sync; `oldbrainfix capture` and `oldbrainfix import` print the first sentence and end with an error. The data of a later version cannot be read here without losing what that version keeps, so installing it again is the only way on.

**Android's stored values.** The alarm plan, its labels, the Nudge and the Changes Nudge, the Done and snoozes queued from notifications and the widget, and the Agenda widget's snapshot are JSON in SharedPreferences, written by this Device's app alone. Each object carries `v` by the rule of ADR 0019, as JSON markers here do: absent or the whole number 1 is version 1, and nothing writes it today; the plan and the queue are arrays, so each of their elements carries its own. Every read catches what does not read: a value that is missing, of another type than a text or a number, or not JSON reads as none, and so does one of a later version, so AlarmReceiver, RearmReceiver and the widget never crash over one. An alarm of the plan or a row of the snapshot that does not read is left out and the rest rings or shows; a label falls back to its name, a Nudge to none, the snapshot to none, with which the widget asks to open the app. The queue loses no tap: an action that does not read, of a kind this version does not apply or of a later version is not handed to the app, and its acknowledgement leaves it queued; a queue text that is no JSON array is kept aside as it was under `unread` before a new tap starts another (a queue of another type than a text is written over), and a new tap's number counts on past every one queued, whatever the stored counter says.

## Codes, files and settings

**Pair code.** Today's codes are version 1 and carry no version: the four layouts (IPv4 or IPv6, the fingerprint whole for the QR or its first 8 bytes for typing) stay told apart by their length, 28, 47, 66 or 85 characters, and every code is written as before, so a phone of 0.1.1 still joins. A code of a later version starts with its version, one character `2` to `9`, and is of none of these lengths and at least 28 characters long. No code of version 1 for a local network starts with such a character (those of 10.x start with `1`, the others with a letter), so a code typed with a character too few or too many stays no code. A code of a length of version 1 is read as version 1, whatever it starts with. Of a later one the code field says "This code comes from a newer Old Brain Fix. Update Old Brain Fix on this Device, then try again." on the phone and the desktop, typed or scanned, and nothing is tried (`pairCodeNeedsUpdate`, `pair_code_needs_update`).

**Sent Item and Backup.** Both already carry `format` (ADR 0019). A JSON object whose `format` is there and not one this version reads, 1 or 2 for a Sent Item and 1 for a Backup, as whole numbers, is of a later version: `SentItemNeedsUpdate` (Dart) or `OpenError::NeedsUpdate` (Rust), and `BackupProblem.needsUpdate` or `Problem::NeedsUpdate`, in place of "no Sent Item" or "no Backup". For a Sent Item this is asked of the file before anything else, and again of the signed file inside an encrypted one; a later format may hold other keys. For a Backup the header line must still say `"type":"oldbrainfix-backup"`, and its first record, `about`, says it too. `"1"`, `1.0` or `null` count as later, as above; before, the Dart core read `1.0` as 1 and the Rust core did not. Both apps show it through the failure dialog: "This file comes from a newer Old Brain Fix." or "This Backup was made by a newer Old Brain Fix.", with "Update Old Brain Fix on this Device, then open it again." A Backup Android's Auto Backup brought back that is of a later format is passed over, as one that is none.

**Keys and Profiles files of the shared folder.** What a keys or Profiles file holds, once opened, is a JSON object that may carry `v`, absent or the whole number 1 for version 1, never written. One of a later version is read not at all, rather than as a file without keys or Profiles, and its writer is counted among the Devices of a newer format (`newer`), which announces that this Device needs an update, as a manifest of a newer format does (ADR 0019). This Device's own keys file of a later version is not written over: only the user's own Devices hold the personal key it is sealed with, so it was this Device's own newer app, and this Device counts itself. Its own Profiles file of a later version is written over as before: anyone holding the Area's key can seal one under its name, so keeping it would let another person stop this Device's Profiles from reaching the Area through the folder.

**Local settings.** A local setting whose value is a JSON object with `v` there and not the whole number 1, or a list holding such an object, was saved by a later version (`laterSetting`, `later_setting`); this version writes neither, and no setting changes its shape. Such a value is never written over or removed by this version, whichever part of either app asks: the store refuses the write and notes the update notice `settings` once, which both apps announce as "An update of Old Brain Fix is needed." with "A setting a newer Old Brain Fix saved on this Device is kept as it is." and "Install the latest Old Brain Fix on this Device." behind the tap. A reader still finds nothing it knows in it and goes on as without the setting, but nothing it does is kept over it. The own Profile's record is left out: it has the rule above, under which one of the user's other Devices may replace it.

## Not covered here

The keys and aliases a signed Profile lists stay as ADR 0017 has them: each counts only when a bound key's signature holds over `oldbrainfix:profile-key:<id>:<key>` or `oldbrainfix:profile-alias:<alias>:<to>`, which says the same whatever a later structure adds beside it. An entry of another shape is still left out and not passed on, since nothing here could check who made it. Sync paths and log entries are handled separately (#60).

## Considered Options

- The version inside each schedule value (rejected: three values would change, and every schedule stored today would read as another shape).
- A garbled version read as 1, as a garbled text marker reads as plain (rejected: a schedule or role read wrongly would be written over from here).
- An unknown role read as Member (rejected: a later read-only role would gain writes on every older Device) or, as before, as no grant (rejected: it strips the person's access, and a Manager here could grant over it).
- A marker inside the Override name (rejected: names are plain and may hold any character).
- A Routine of a later version as a `Routine` without a schedule (rejected: every reader of a schedule in both cores and both apps would have to handle its absence; a type of its own keeps them as they are).
- A database of a later version opened read-only, showing what this version can read of it (rejected: what this version reads of a later one's tables can be wrong, and the alarms and Captures that would follow from it could not be kept).
- `user_version` 0 kept for version 1, as markers in the log keep it absent (rejected: every open would have to probe the columns again to tell a database from before 0.1.0 from today's).
- The column probes kept for a database at 0 (rejected: no released version wrote one without the columns).
- A version byte in today's pair codes (rejected: a phone of 0.1.1 could no longer join a Device of this version).
- Any code of an unknown length read as one of a later version (rejected: a code typed with a character too few would say "update the app" instead of "check the code").
- The own Profiles file of a later version kept, as the own keys file is (rejected: the Area's key is held by other people, so any of them could freeze it).
- The update notice of a setting kept at every refused write (rejected: one announcement is enough; the value stays either way).

## Consequences

- No value stored today changes: version 1 writes nothing new, every fixture before this one stayed byte for byte, and the `markers` fixture holds the values of a later version.
- A times value with a part that is no `HH:MM`, which no version wrote, now makes the Routine one of a later version instead of losing that time.
- A Sent Item whose Routine has such times is unreadable, as one with an unreadable rule already was.
- Nothing changes for the user of this version alone: the note shows only once a later version writes one of these values.
- The first open by this version writes `user_version` 1 into the database; the version before it neither reads nor minds it. A database of a build from before 0.1.0 that was never opened since no longer gains its missing columns.
- `schema.sql` among the fixtures holds the version beside the tables, so both cores record the same one.
- No code or file written today changes; `pair_codes.json` holds codes of a later version beside those no code, and `later_formats.json` what Sent Items, Backup headers, keys and Profiles files and local settings of a later version come to in both cores.
- A Backup header with `"format":1.0` no longer opens on a phone; no version wrote one.
- A setting of a later version a reader cannot use stays without effect here until the app is updated, and its update notice comes once.
